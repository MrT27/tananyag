Git / GitHub 11. évfolyam 4. óra

Konfliktusok feloldása Gitben

Ugyanaz a sor, két külön változat: felismerjük az ütközést, és együtt készítjük el a végleges megoldást.

1. Mi az a konfliktus?

Az előző órán közösen dolgoztatok egy weboldalon. Most mindketten ugyanazt a címsort módosítjátok, eltérő szövegre. A Git sok változtatást automatikusan egyesít, de az egymásnak ellentmondó módosításokról nektek kell dönteni. Ezt nevezzük összefésülési konfliktusnak (merge conflict).

A konfliktus nem jelenti azt, hogy elveszett a munka. A Git megáll az egyesítés közben, és megmutatja a vitás részeket. A kész tartalmat ti állítjátok össze.

Nem minden közös fájlmódosítás okoz konfliktust. Eltérő részek gyakran automatikusan összefésülhetők. Konfliktus például akkor is lehet, ha valaki töröl egy fájlt, amelyet a társa módosít.

2. Páros gyakorlat – közös kiindulópont

Dolgozzatok a 3. óra közös repositoryjában. Legyen egy A tanuló és egy B tanuló. Mindketten a saját gépeteken dolgozzatok, és várjátok meg egymást a jelzett pontokon!

  • A parancsokat a projekt mappájában, a VS Code termináljában futtassátok.
  • A példában a távoli repository neve origin, a közös ág neve main. A saját ágatok nevét a git branch --show-current paranccsal nézhetitek meg; eltérő névnél ezt használjátok a main helyett.
  • A git status induláskor tiszta munkakönyvtárat jelezzen. A korábbi munkát előbb mentsétek és commitoljátok.

A tanuló: frissíts, majd az index.html egyik meglévő h1 címsorát alakítsd az alábbira. A fájl többi részét tartsd meg!

git pull --ff-only origin main
<h1>Közös weboldal</h1>
git add index.html
git commit -m "Konfliktusgyakorlat közös címsora"
git push origin main

Ha ez a címsor már pontosan így szerepel a közös változatban, nincs szükség újabb commitra. B tanuló: most frissíts!

git pull --ff-only origin main
git status
Ellenőrzési pont: mindkét gépen ugyanaz a „Közös weboldal” címsor szerepeljen, és ne legyen nem commitolt módosítás. Ha a frissítés hibát jelez, előbb rendezzétek az eltérést a tanárral.

3. Két külön módosítás ugyanarra a sorra

Most szándékosan ne pulloljatok egymás módosításai között! Mindketten a közös kiinduló változatot szerkesztitek.

A tanuló

<h1>Osztályunk bemutatkozása</h1>
git add index.html
git commit -m "A tanuló: új főcím"
git push origin main

B tanuló

<h1>Üdvözlünk az oldalunkon!</h1>
git add index.html
git commit -m "B tanuló: új főcím"

A tanuló pusholjon először. Miután ez sikerült, B is próbálja meg:

git push origin main
B feltöltését a Git várhatóan elutasítja (rejected, fetch first vagy non-fast-forward). A távoli ágon már van olyan commit, amely B helyi történetéből hiányzik. Ez még nem maga a merge conflict. Ne használjatok force push-t: előbb egyesítjük a két munkát.

4. A konfliktus előidézése

B tanuló töltse le és próbálja összefésülni A módosítását:

git pull --no-rebase --no-ff origin main

A --no-rebase ehhez a gyakorlathoz merge-alapú egyesítést választ. A --no-ff az esetleg beállított „csak fast-forward” mód helyett is lehetővé teszi a merge-öt. Nem állítjuk át a Git globális beállításait.

CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.
git status

A pontos üzenet eltérhet. A status az index.html fájlt például both modified állapottal mutatja. Az egyesítés folyamatban van; most a fájlt kell javítani.

5. A konfliktusjelölések olvasása

B gépén nyissátok meg az index.html fájlt. Az alapértelmezett jelölés ilyen:

<<<<<<< HEAD
<h1>Üdvözlünk az oldalunkon!</h1>
=======
<h1>Osztályunk bemutatkozása</h1>
>>>>>>> a-beerkezo-commit-azonositoja
  • <<<<<<< HEAD: a jelenlegi helyi változat kezdete, itt B szövege.
  • =======: a két változat elválasztója.
  • >>>>>>>: a beérkező változat vége, itt A szövege. Utána valódi commitazonosító vagy címke állhat.

Más konfliktusmegjelenítési beállításnál a közös kiinduló változat is látszhat egy ||||||| jelölés után. Ezek a jelölések nem HTML-kódok: a feloldás végén mindet el kell távolítani.

6. Közösen eldöntjük a végleges tartalmat

Beszéljétek meg, mi legyen a cím. Választhatjátok az egyik változatot, vagy írhatjátok a kettőből ezt:

<h1>Üdvözlünk osztályunk bemutatkozó oldalán!</h1>
  1. B jelölje ki a teljes konfliktusos blokkot a jelölésekkel együtt.
  2. Cserélje a fenti egyetlen h1 sorra, majd mentse a fájlt.
  3. A fájl többi tartalmát tartsa meg. Ha több konfliktusos blokk van, mindegyiket rendezze.
  4. Nyissátok meg az oldalt böngészőben, és ellenőrizzétek a címet és a megjelenést.
A VS Code kínálhat Current / Incoming / Both választást vagy merge szerkesztőt. Ebben a merge-ben a Current B helyi, az Incoming A beérkező változata. A Both mindkét részt megtarthatja, ezért két címsort is eredményezhet. Mindig olvassátok el a végeredményt; a kézi szerkesztés is teljes értékű megoldás.

7. A feloldás rögzítése és feltöltése

B tanuló ellenőrizze a javítást, majd jelölje megoldottnak a fájlt:

git diff --check
git add index.html
git status
git diff --cached

A git diff --check többek között megmaradt konfliktusjelölésekre és szóközhibákra figyelmeztethet; nem helyettesíti a tartalom ellenőrzését. A git add jelzi a Gitnek, hogy ezt a fájlt feloldottuk. A status szerint minden konfliktus rendezett legyen; az egyesítést még commit zárja le.

git commit -m "Címsor konfliktusának közös feloldása"
git push origin main

Ez a commit összekapcsolja a két fejlesztési előzményt. Most A tanuló is frissítsen:

git pull --ff-only origin main
git status
git log --oneline --graph -6
Mindkét gépen és GitHubon is ugyanaz a végleges címsor szerepeljen. Mindkét eredeti commit és a feloldást rögzítő merge commit is legyen meg a történetben.

8. Ha elakadtál

JelenségTeendő
Push elutasítvaNézd meg az okot. Ha új távoli commit az ok, töltsd le és egyesítsd; a hitelesítési hiba külön probléma.
Local changes would be overwrittenA helyi, nem commitolt munkát előbb mentsd és commitold. Ez nem ugyanaz, mint egy már megkezdett merge konfliktusa.
Unmerged pathsMég van feloldatlan fájl. Szerkeszd meg, mentsd, majd git add-dal jelöld rendezettnek.
Nincs konfliktus a gyakorlatbanEllenőrizzétek, hogy ugyanazt a sort, közös kiindulópontból, eltérően módosítottátok-e, és B közben nem frissített-e.

Ha a git status szerint merge van folyamatban, és inkább újrakezdenéd az egyesítést:

git merge --abort
git status

Ez megszakítja a folyamatban lévő merge-öt, és megpróbálja visszaállítani az előtte lévő állapotot. A merge közben végzett feloldási munka elvész; az előtte készült saját commitok megmaradnak. Ezért indultunk tiszta munkakönyvtárból. A parancs nem egy már elkészült merge commit visszavonására való.

9. Önálló páros feladat és beadás

Cseréljetek szerepet, és idézzetek elő új konfliktust a meglévő style.css egy közösen kiválasztott color sorában!

  1. Egyeztessetek és szinkronizáljatok egy közös kiinduló értéket.
  2. Mindketten írjatok eltérő színt ugyanarra a sorra, majd commitoljatok.
  3. Ezúttal B pusholjon először, A kezelje az elutasítást és az egyesítést.
  4. Egyezzetek meg a végleges színben; oldjátok fel, ellenőrizzétek és commitoljátok a konfliktust.
  5. Push után a másik fél is frissítsen.
Beadás: a közös repository linkje, mindkét tanuló neve és a két konfliktusfeloldó commit azonosítója. Röviden írjátok le, milyen eltérő módosítások ütköztek, és miért a végleges változatot választottátok!

10. Amit meg kell jegyezni

Megnézem → egyeztetek → szerkesztek → mentek → ellenőrzök → add → commit → push.

A rendszeres pull, a kisebb commitok és a feladatok egyeztetése csökkenti a konfliktusok esélyét. A konfliktus feloldása tartalmi döntés: nem az a cél, hogy automatikusan az egyik fél változata győzzön.

Ellenőrző kérdések és válaszok
  • Az elutasított push már konfliktus? Nem; a tartalmi konfliktus az egyesítés során derül ki.
  • Mit jelent itt a HEAD oldala? Az egyesítést végző gép jelenlegi helyi változatát.
  • Elég kitörölni a jelöléseket? Nem; értelmes, működő végleges tartalmat kell összeállítani.
  • Mit jelez a git add? Hogy az adott fájl feloldott változata készen áll a commitra.
  • Miért kell a másik félnek is pullolnia? Hogy megkapja a közös végeredményt.
